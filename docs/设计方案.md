## 1. 项目概述

### 1.1 产品定位

CubicleChat 是一款面向企业内网/局域网环境的即时通讯工具，**无需服务器部署、无需互联网，开箱即用**。用户只需在同一 Wi-Fi 或有线局域网内，即可自动发现彼此并开始通讯。

### 1.2 设计原则

| 原则 | 说明 |
|------|------|
| 零服务器依赖 | 所有通信在局域网内点对点完成，无中心节点 |
| 轻量快速 | 安装包 < 80 MB，启动时间 < 2 秒 |
| 数据本地存储 | 所有历史消息与文件元数据存储于本机 SQLite |
| 跨平台一致性 | Windows 10+、Linux（Ubuntu 20.04+）界面与体验一致 |

### 1.3 目标用户

| 用户类型 | 典型场景 |
|---------|---------|
| 小型办公团队 | 日常工作沟通，替代微信/钉钉等需要互联网的工具 |
| 工厂/制造业 | 封闭内网环境下的跨部门沟通 |
| 学校/实验室 | 局域网内文件共享与即时沟通 |
| 保密要求高的单位 | 数据不出内网，合规要求满足 |

### 1.4 功能全景


### 3.4 核心数据流

#### 发送消息流程

```
用户输入 Enter
    │
    ▼
[Renderer] MessageInput.tsx
    │ ipcRenderer.invoke('msg:send', {to, content})
    ▼
[Main] message.ipc.ts (参数验证)
    │
    ▼
[Main] MessageService.send()
    ├─ MessageRepo.save() → SQLite (写入本地)
    └─ UdpMessenger.send() → UDP Socket → 目标 IP:2425
                                               │
                                               ▼
                                          [对方 Main]
                                          UdpMessenger.onReceive()
                                               │
                                               ▼
                                          MessageService.receive()
                                               ├─ MessageRepo.save() → SQLite
                                               └─ BrowserWindow.webContents.send('msg:receive', data)
                                                        │
                                                        ▼
                                                  [对方 Renderer]
                                                  更新 messageStore → 渲染新消息气泡
```

#### 文件传输流程

```
拖放文件
    │
    ▼
[Renderer] DropZone 组件
    │ ipcRenderer.invoke('file:send', {to, filePath})
    ▼
[Main] FileService.initTransfer()
    ├─ 读取文件元信息（大小、名称、MD5）
    ├─ 图片则生成缩略图（sharp, 240×240）
    ├─ 通过 UDP 发送 FILE_NOTIFY（含缩略图 Base64）
    └─ 等待对方 TCP 连接
         │
         ▼ (对方接受)
    [Main] TcpTransfer.startSend()
         ├─ 建立 TCP 连接，握手
         ├─ 分块发送（512KB/块）
         ├─ 推送进度到渲染进程
         └─ 完成后 MD5 校验
```

## 4. UDP 协议与用户发现机制

### 4.1 协议选型

| 协议 | 用途 | 端口 | 说明 |
|------|------|------|------|
| **UDP** | 用户发现广播、即时消息 | 2425 | 与飞秋（FeiQ）同端口，未来可互通 |
| **TCP** | 文件/图片可靠传输 | 2426 | 保证数据完整性 |

### 4.2 用户发现机制

采用 **UDP 广播 + 心跳** 模式：

```
应用启动
    │
    ├─ 绑定 UDP 0.0.0.0:2425
    ├─ 监听所有 IPv4 接口的广播
    └─ 发送 ONLINE 广播包 → 255.255.255.255:2425
         │
         ▼
    局域网内所有用户收到广播
         └─ 每个收到广播的用户回复 ONLINE_ACK 单播包

定时任务：每 30 秒发送 HEARTBEAT 广播
    └─ 超过 90 秒未收到 HEARTBEAT → 标记用户离线
```

#### 状态机

```
         应用启动
             │
             ▼
       ┌─────────┐  收到 HEARTBEAT / ONLINE_ACK
       │  ONLINE  │◄──────────────────────────┐
       └─────────┘                             │
             │                                 │
             │  90s 无心跳                     │
             ▼                                 │
       ┌─────────┐                             │
       │ TIMEOUT  │  收到任意包 ─────────────►─┘
       └─────────┘
             │
             │  30s 后仍无响应
             ▼
       ┌─────────┐
       │ OFFLINE  │
       └─────────┘
```

### 4.3 UDP 数据包格式

所有 UDP 数据包使用 **JSON** 编码（UTF-8），外层固定格式：

```typescript
interface UdpPacket {
  // 协议头（固定）
  magic: "CCHT";            // 魔数，过滤无关广播包
  version: 1;               // 协议版本
  type: PacketType;         // 包类型
  msgId: string;            // UUID，用于去重/ACK
  timestamp: number;        // Unix timestamp（毫秒）

  // 发送方信息
  from: {
    userId: string;         // UUID（本机生成，持久化）
    nickname: string;       // 显示名称
    ip: string;             // 发送方 IP
    port: number;           // TCP 文件传输端口（2426）
    avatar?: string;        // Base64 缩略头像（64×64 JPEG，最大 8KB）
    status: UserStatus;     // 'online' | 'busy' | 'away'
    version: string;        // 客户端版本号
  };

  payload?: Record<string, unknown>;
}
```

#### 包类型枚举

```typescript
type PacketType =
  | "ONLINE"          // 上线广播
  | "ONLINE_ACK"      // 上线回复
  | "HEARTBEAT"       // 心跳广播
  | "OFFLINE"         // 主动下线
  | "TEXT"            // 文本消息
  | "TEXT_ACK"        // 消息已接收确认
  | "WITHDRAW"        // 撤回消息
  | "FILE_NOTIFY"     // 文件传输通知
  | "FILE_ACCEPT"     // 接受文件
  | "FILE_REJECT"     // 拒绝文件
  | "GROUP_CREATE"    // 创建群组
  | "GROUP_INVITE"    // 群组邀请
  | "GROUP_MESSAGE"   // 群消息
  | "GROUP_LEAVE"     // 离开群组
  | "TYPING"          // 正在输入...
  | "STATUS_CHANGE";  // 状态变更
```

#### 各类型 Payload 定义

| type | payload 字段 | 说明 |
|------|-------------|------|
| `TEXT` | `{to, content, contentType, replyTo?}` | 单聊/群聊文本消息 |
| `TEXT_ACK` | `{ackMsgId}` | 消息确认 |
| `WITHDRAW` | `{targetMsgId, to}` | 撤回消息 |
| `FILE_NOTIFY` | `{to, transferId, fileName, fileSize, fileType, fileMd5, isImage, tcpPort, thumbnailData?}` | 文件传输协商 |
| `FILE_ACCEPT` | `{transferId, offset?}` | 接受（offset 用于断点续传） |
| `FILE_REJECT` | `{transferId, reason?}` | 拒绝 |
| `TYPING` | `{to, isTyping}` | 正在输入提示 |
| `GROUP_CREATE` | `{groupId, groupName, memberIds[]}` | 创建群组 |
| `GROUP_MESSAGE` | `{to: groupId, content, contentType}` | 群消息 |

### 4.4 消息可靠性

UDP 不保证投递，应用层实现 ACK + 超时重试：

```
发送方                                接收方
   │                                    │
   │──── TEXT (msgId: "abc") ──────────►│
   │                                    │  写入数据库 + 发 TEXT_ACK
   │◄─── TEXT_ACK (ackMsgId: "abc") ───│
   │                                    │
   │  收到 ACK → 标记"已送达"            │
```

**重试策略：**

| 参数 | 值 |
|------|------|
| 最大重试次数 | 3 |
| 初始延迟 | 500 ms |
| 退避倍数 | 2× |
| 重试间隔 | 500ms → 1000ms → 2000ms |
| 3 次失败后 | 标记"发送失败"，显示红色感叹号 + 重试按钮 |

**消息去重：** 使用 LRU Cache 缓存最近 1000 条已处理 msgId，丢弃重复包。

**消息排序：** 每条消息携带 timestamp（毫秒），UI 按时间戳排序。容忍时钟差 ±60 秒，同毫秒消息按 msgId 字典序。

### 4.5 多网卡与网络环境

- 默认对**所有非回环 IPv4 接口**发送广播
- 设置界面提供手动选择网络接口选项
- 监听 `network-change` 系统事件，自动重新广播
- 端口冲突时自动提示用户更改端口

### 4.6 流量估算

| 场景 | 单包大小 | 频率 | 100 用户带宽 |
|------|---------|------|-------------|
| HEARTBEAT | ~300 B | 30s/次 | ~1 KB/s |
| TEXT 消息 | ~500 B | 按需 | 按聊天量 |
| FILE_NOTIFY | ~1 KB | 按需 | 忽略 |
| ONLINE 广播 | ~500 B | 启动时 | 一次性 |

## 5. 数据库设计

### 5.1 技术方案

- **引擎**：SQLite（better-sqlite3）
- **ORM**：Drizzle ORM
- **日志模式**：WAL（Write-Ahead Logging）
- **全文搜索**：SQLite FTS5

**数据库配置：**

```typescript
sqlite.pragma('journal_mode = WAL');       // WAL 模式
sqlite.pragma('synchronous = NORMAL');     // 性能与安全平衡
sqlite.pragma('cache_size = -64000');      // 64MB 缓存
sqlite.pragma('foreign_keys = ON');        // 外键约束
sqlite.pragma('temp_store = MEMORY');      // 临时表存内存
```

### 5.2 ER 关系图


```sql
CREATE VIRTUAL TABLE messages_fts USING fts5(
  message_id UNINDEXED,
  content,
  content='messages',
  content_rowid='rowid'
);

-- FTS 同步触发器
CREATE TRIGGER messages_fts_insert AFTER INSERT ON messages BEGIN
  INSERT INTO messages_fts(rowid, message_id, content)
  VALUES (new.rowid, new.message_id, new.content);
END;
CREATE TRIGGER messages_fts_delete AFTER DELETE ON messages BEGIN
  INSERT INTO messages_fts(messages_fts, rowid, message_id, content)
  VALUES('delete', old.rowid, old.message_id, old.content);
END;

-- 文件
CREATE INDEX idx_files_peer ON files(peer_id, created_at DESC);
CREATE INDEX idx_files_status ON files(status);
```

### 5.5 数据清理策略

每天凌晨 3:00（或应用启动时检查）自动执行：

1. 删除超过保留天数的旧消息
2. 删除已完成的旧文件传输记录（实际文件不删除）
3. 清理孤立会话
4. 执行 `VACUUM` 压缩数据库

**180 天活跃用户估算：** 数据库大小 < 30 MB

## 6. 文件传输模块

### 6.1 传输协议

| 阶段 | 协议 | 说明 |
|------|------|------|
| 传输协商 | UDP | FILE_NOTIFY / FILE_ACCEPT / FILE_REJECT |
| 数据传输 | TCP | 分块传输，保证可靠性 |

### 6.2 完整传输流程

```
发送方                                    接收方
   │
   │  1. 用户触发（拖放/选择文件/粘贴图片）
   │  2. 读取文件元信息（名称、大小、MD5）
   │     图片则生成缩略图（sharp 240×240）
   │
   │──3. UDP FILE_NOTIFY ─────────────────►│
   │     { transferId, fileName, fileSize,   │
   │       fileMd5, tcpPort, thumbnailData } │
   │                                         │  4. 展示接收请求（嵌入式面板）
   │                                         │
   │◄──5. UDP FILE_ACCEPT ──────────────────│
   │     { transferId, offset: 0 }            │
   │
   │  6. 建立 TCP 监听，等待连接
   │                           TCP 连接 ────►│
   │──── HANDSHAKE { transferId, offset } ──►│  验证 transferId
   │◄─── HANDSHAKE_OK ─────────────────────  │
   │
   │  7. 分块发送
   │──── CHUNK { seq, data[512KB] } ────────►│  写入本地文件
   │──── CHUNK { seq, data[512KB] } ────────►│
   │──── CHUNK_END { fileMd5 } ─────────────►│  验证 MD5
   │◄─── TRANSFER_DONE ─────────────────────│
   │
   │  8. 双方更新 DB 状态 = completed
```

### 6.3 断点续传

```
发送方                                    接收方
   │  (重新发起传输)                        │
   │──── UDP FILE_NOTIFY ───────────────────►│
   │                                         │  检查本地部分文件
   │◄─── UDP FILE_ACCEPT ───────────────────│
   │     { transferId, offset: 327680 }      │  (已有 320KB)
   │
   │  从 offset 处继续发送剩余数据            │  以 append 模式写入
   │──── CHUNK { seq: 641, data } ──────────►│
```

### 6.4 TCP 消息帧格式

所有 TCP 消息使用 **长度前缀帧**（Length-Prefixed Frame）：

```
┌──────────────┬────────────────────────────────┐
│  长度(4字节)  │  消息体（JSON 或二进制数据）     │
│  Big-Endian  │  最大 512KB + 8字节头           │
└──────────────┴────────────────────────────────┘
```

控制消息类型：`HANDSHAKE` | `HANDSHAKE_OK` | `CHUNK` | `CHUNK_END` | `TRANSFER_DONE` | `ERROR`

### 6.5 分块大小策略

| 文件大小 | 分块大小 | 原因 |
|---------|---------|------|
| < 1 MB | 128 KB | 小文件快速传输 |
| 1 - 100 MB | 512 KB | 平衡内存与吞吐 |
| > 100 MB | 1 MB | 减少 IPC 开销 |

### 6.6 并发控制

- 同时最多 **3 个文件传输**（发送 + 接收各 3 个）
- 超出限制的传输任务进入队列等待
- 用户可在设置中配置传输速度上限（ThrottledStream）

### 6.7 图片处理

| 功能 | 实现 |
|------|------|
| 缩略图生成 | sharp, 最大 240×240, JPEG quality 75 |
| 缩略图传输 | 随 FILE_NOTIFY 以 Base64 发送（~32KB） |
| 剪贴板粘贴 | 监听 paste 事件，blob → temp 文件 → 预览 → 发送 |
| 拖放发送 | DropZone 组件监听 dragover/drop |
| 格式支持 | JPEG / PNG / GIF（静态）/ WebP / BMP→PNG / TIFF→JPEG |
| 大小限制 | 单张最大 20 MB |

### 6.8 安全校验

| 机制 | 说明 |
|------|------|
| MD5 校验 | 传输完成后比对 fileMd5，失败自动重试（最多 2 次） |
| 危险扩展名 | .exe/.msi/.bat/.cmd/.ps1 等显示警告（v1.0 不强制阻止） |
| 路径穿越防护 | `path.basename()` 清理文件名，校验目标路径在下载目录内 |
| 磁盘空间检查 | 传输前检查可用空间，不足时拒绝接收 |

### 6.9 错误处理

| 错误场景 | 处理策略 |
|---------|---------|
| TCP 端口被占用 | 自动尝试 2426-2430，超出范围提示用户 |
| 传输超时（60s 无数据） | 标记失败，显示"续传"按钮 |
| MD5 校验失败 | 自动从断点重新传输（最多重试 2 次） |
| 磁盘空间不足 | 传输前通知用户并拒绝 |
| 对方突然离线 | 暂停传输，对方上线后可续传 |
| 文件被删除（传输中） | 发送方报错，通知接收方"文件已不可用" |

## 7. UI/UX 设计规范

### 7.1 设计理念

- **内容优先**：界面服务于对话，不抢戏
- **信息密度适中**：紧凑但不拥挤，适合长时间使用
- **嵌入式面板**：功能通过侧边栏和内嵌面板展示，**严禁弹窗**

- **圆角风格**：统一 8px / 12px 圆角，柔和而专业
- **轻量动效**：交互反馈通过微动效实现，不使用长过场动画

## 8. 接口设计（IPC Channel）

### 8.1 IPC Channel 规范

| Channel | 方向 | 描述 | 参数 |
|---------|------|------|------|
| `msg:send` | 渲染→主 | 发送消息 | `{to, content, contentType, replyTo?}` |
| `msg:receive` | 主→渲染 | 收到新消息 | 消息对象 |
| `msg:withdraw` | 渲染→主 | 撤回消息 | `{messageId, conversationId}` |

| `msg:search` | 渲染→主 | 搜索历史 | `{keyword, conversationId?}` |
| `msg:history` | 渲染→主 | 加载历史 | `{conversationId, limit, before?}` |
| `user:online` | 主→渲染 | 用户上线通知 | 用户对象 |
| `user:offline` | 主→渲染 | 用户离线通知 | `{userId}` |
| `user:list` | 渲染→主 | 获取在线用户 | `void` |
| `user:update` | 渲染→主 | 更新个人信息 | `{nickname?, avatar?, status?}` |
| `file:send` | 渲染→主 | 发起文件传输 | `{to, filePath}` |
| `file:progress` | 主→渲染 | 传输进度 | `{transferId, percent, speed}` |
| `file:accept` | 渲染→主 | 接受文件 | `{transferId}` |
| `file:reject` | 渲染→主 | 拒绝文件 | `{transferId}` |
| `file:list` | 渲染→主 | 获取文件列表 | `{filter?, sort?}` |
| `file:open` | 渲染→主 | 打开文件 | `{fileId}` |
| `group:create` | 渲染→主 | 创建群组 | `{groupName, memberIds[]}` |
| `group:invite` | 渲染→主 | 邀请成员 | `{groupId, userIds[]}` |
| `settings:get` | 渲染→主 | 读取设置 | `{key?}` |
| `settings:set` | 渲染→主 | 保存设置 | `{key, value}` |
| `typing:start` | 渲染→主 | 开始输入 | `{to}` |
| `typing:stop` | 渲染→主 | 停止输入 | `{to}` |
| `typing:receive` | 主→渲染 | 对方正在输入 | `{from, to}` |

## 9. 安全架构

### 9.1 Electron 安全配置

```typescript
new BrowserWindow({
  webPreferences: {
    nodeIntegration: false,        // 禁止渲染进程直接访问 Node
    contextIsolation: true,        // 启用上下文隔离
    sandbox: true,                  // 启用沙箱
    preload: path.join(__dirname, 'preload.js'),
  },
});
```

### 9.2 Preload 安全边界

```typescript
// 仅暴露必要的 IPC Channel 白名单
contextBridge.exposeInMainWorld('ipc', {
  send: (channel: string, data: unknown) => {
    const allowed = ['msg:send', 'file:send', 'settings:set', ...];
    if (allowed.includes(channel)) ipcRenderer.invoke(channel, data);
  },
  on: (channel: string, callback: Function) => {
    const allowed = ['msg:receive', 'user:online', 'file:progress', ...];
    if (allowed.includes(channel)) {
      ipcRenderer.on(channel, (_, ...args) => callback(...args));
    }
  },
});
```

### 9.3 安全措施总结

| 层面 | 措施 | 版本 |
|------|------|------|
| 进程隔离 | nodeIntegration=false, contextIsolation=true, sandbox=true | v1.0 |
| IPC 白名单 | preload 仅暴露已审核的 channel | v1.0 |
| 文件传输 | MD5 完整性校验、路径穿越防护、危险扩展名警告 | v1.0 |
| 消息加密 | 不加密（局域网可信环境） | v1.0 |
| 消息加密 | AES-256 端对端加密 | v1.1 规划 |
| 本地数据 | SQLite 不加密 | v1.0 |
| 本地数据 | SQLCipher 加密 | v1.1 规划 |

## 10. 性能优化策略

| 场景 | 策略 |
|------|------|
| 历史消息加载 | 虚拟滚动（react-window），每次渲染 50 条 |
| 大量在线用户 | 列表按状态分组，懒加载 |
| 图片缩略图 | 主进程生成缓存，渲染进程只显示缩略图 |
| 频繁 IPC 调用 | 批量合并，减少进程切换开销 |
| 数据库写入 | WAL 模式 + 消息队列缓冲 100ms 批量写入 |
| 内存防护 | 聊天记录超 500 条时从内存清除早期消息 |
| 动效性能 | 仅动画 GPU 属性（transform, opacity），avoid layout thrashing |
| 减少动效 | 尊重 `prefers-reduced-motion` 系统设置 |

### 性能指标要求

| 指标 | 要求 |
|------|------|
| 消息发送延迟 | < 100 ms（局域网 1Gbps） |
| 应用启动时间 | < 2 秒（冷启动） |
| 内存占用 | 空闲 < 80 MB |
| CPU 占用 | 空闲 < 1%，消息处理 < 5% |
| 文件传输速度 | 不低于网络带宽 80% |
| 最大在线用户 | 200 个并发 |
